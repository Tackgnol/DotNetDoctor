# Effective analyzer configuration

This is the precedence contract the scanner actually implements, with the test
that proves each row. Behavior not listed here is not claimed.

## Precedence (highest wins)

1. **Source suppressions** - `#pragma warning disable`, `[SuppressMessage]`.
   Honored by the analyzer driver; the scanner runs with
   `reportSuppressedDiagnostics: false`, so a suppressed occurrence never
   appears. *(integration: the `#pragma`-suppressed `CA2200` in
   `spike/fixtures/BadProject` is not reported.)*
2. **Project `NoWarn` / explicit `SpecificDiagnosticOptions`** - a rule the
   project's build explicitly sets to `none` (`<NoWarn>CA2200</NoWarn>`) stays
   off. The profile does **not** resurrect it; it is listed under
   `analysis.rulesDisabledOrSkipped`.
   *(`NoWarn_in_the_project_is_not_resurrected_by_the_profile`.)*
3. **Repository `.editorconfig`, per file or per directory** -
   `dotnet_diagnostic.<ID>.severity` from any `.editorconfig` that applies to a
   file wins over the profile severity for that file. A nested `.editorconfig`
   overrides a shallower one. Findings whose effective severity came from
   `.editorconfig` are marked `policySource: analyzer-config`.
   *(`Repository_editorconfig_raises_severity_over_the_profile_and_is_marked_analyzer_config`,
   `Per_directory_editorconfig_none_suppresses_and_generated_file_is_not_reported`.)*
4. **`.repo-doctor.json` per-rule overrides** - override profile `severity` /
   `scope`; an override that omits a field inherits it from the profile rule; a
   rule not selected by the profile needs both fields.
   *(Core: `ProfileResolverTests`.)*
5. **Selected profile severity** - the fallback default for a selected rule when
   nothing above specifies one. Supplying it also **enables a
   disabled-by-default rule** (e.g. `CA2000`, whose descriptors are
   `IsEnabledByDefault = false`).
   *(`Disabled_by_default_rule_runs_when_the_profile_selects_it`.)*
6. **Bundled analyzer defaults** - only rules in the shipped catalog exist; only
   the bundled analyzer instances run (never the scanned repo's own copies).

## Mechanism

The scanner never rewrites `CompilationOptions.SpecificDiagnosticOptions` for
selected rules. Instead it wraps the project's real
`SyntaxTreeOptionsProvider` (`FallbackSyntaxTreeOptions`): the inner provider -
built by `MSBuildWorkspace` from the repository's `.editorconfig` files and
`NoWarn` - is consulted first (per tree, then global); the profile severity is
returned only when the inner provider has nothing for that rule id. The
project's real `AnalyzerOptions` (its `AnalyzerConfigOptionsProvider` and
additional files) is passed through to `CompilationWithAnalyzers` unchanged, so
analyzer behavior options configured in the repository are preserved.

`TreatWarningsAsErrors` is a build policy and is ignored for scanner severity;
the effective severity of a finding is what Roslyn computes from the sources
above, reported as `findings[].severity`.

## Scope

`scope: production` rules are not evaluated in test projects. A project is a
test project when its evaluated metadata says so - `<IsTestProject>true</...>`
or a metadata reference to a known test framework
(`xunit`, `nunit.framework`, `Microsoft.NET.Test.Sdk`, `MSTest`, ...). Filename
is not used.
*(`Production_scoped_rule_is_skipped_in_a_test_project`,
`Production_scoped_rule_still_applies_to_a_non_test_project`.)*

## Generated code

A finding is dropped when its syntax tree is marked generated
(`<auto-generated>` header / `generated_code = true`) or its path is under
`obj/` or ends in `.g.cs`, `.g.i.cs`, `.Designer.cs`, `.generated.cs`. Generated
files remain part of the compilation.
*(covered by `Per_directory_editorconfig_none_suppresses_and_generated_file_is_not_reported`.)*

## Reported-location exclusions

`.repo-doctor.json` `exclude` globs filter **reported finding locations only**,
not compilation inputs. Matching is case-sensitive on `/`-normalized
repository-relative paths (`Microsoft.Extensions.FileSystemGlobbing`). Excluded
counts are surfaced as an `info` problem on the `exclude` stage; the patterns
are recorded in `policy.exclusions`.
*(`Exclude_globs_filter_reported_locations_only`, Core `ExcludeMatcherTests`.)*

## Project configuration checks

The opt-in `profiles/dotnet-code-quality.json` profile adds five engine rules. For each supported subject project, RepoDoctor asks the selected SDK for final evaluated properties with `dotnet msbuild -getProperty`; imported and conditional values therefore take effect.

| Rule | Complete-policy value |
| --- | --- |
| `RD1001` | `Nullable` is `enable` or `warnings` |
| `RD1002` | .NET analyzers and analyzer execution during build are not explicitly disabled |
| `RD1003` | `TreatWarningsAsErrors=true`, code-analysis warnings are not exempted, and `WarningsNotAsErrors` is empty |
| `RD1004` | `EnforceCodeStyleInBuild=true` |
| `RD1005` | `ManagePackageVersionsCentrally=true` |

These checks cover the selected `Debug` configuration and supported target framework. They do not certify every CI configuration or local source suppression. Findings have no invented source location; their messages show observed values and their evidence hash records those values. Control them through the selected profile or `.repo-doctor.json`; source `.editorconfig` and location exclusions do not suppress project-configuration findings. Evaluation or SDK-identity failure makes the scan incomplete.

To adopt the experimental profile, copy `profiles/dotnet-code-quality.json` into `.repo-doctor/` and point the repository configuration at it:

```json
{
  "schemaVersion": 1,
  "profile": ".repo-doctor/dotnet-code-quality.json",
  "rules": {},
  "exclude": []
}
```

The profile gates warning-or-higher findings at `unknown` confidence. Its `info` naming, cancellation-candidate, warning-policy, style, and package-governance findings remain visible without blocking.

For an ad-hoc run that leaves repository configuration untouched, use `repo-doctor scan <target> --profile <profile-file>`. `--profile` and `--config` are mutually exclusive.

The source article also recommends reviewing boolean parameters, vague type names, regions, single-implementation interfaces, inheritance, and eagerly materialized return types. This profile does not turn those contextual design choices into diagnostics: their presence alone is not evidence of a defect. Sonar, Roslynator, and additional test-analyzer packages are likewise not part of this profile.

## Not yet covered (tracked for later milestones)

- Cross-project symbol binding and source-generated types across a solution
  (needs the multi-project fixtures added with baseline work in M4).
- One failed project in a solution leaving other results intact (M4 fixtures).
- `.editorconfig` change detection for baseline compatibility (M4, section 11.2).
